## 1. 结论与推荐范围

Element Plus 不再是必须保留的前提。先验证替代方案，再确定全站是否替换。
优先对照 **Naive UI** 与 **Nuxt UI**，以前端现有实现为基线。
Naive UI 代表完整后台组件、中文表单与较少新增样式基础设施；Nuxt UI 代表 Reka/TanStack 组合之上的成套封装和更直接的视觉定制。
这是进入验证的理由，不是“已经比现有项目更快、更可用”的结论。

shadcn-vue / Reka UI / TanStack 手工组合暂不进入首轮：自由度高，但本项目需要自己组合和持续维护更多表格、表单与样式行为。
PrimeVue 功能值得参考，但官方已宣布 5 起采用新的非开源授权；本轮优先开源候选，不默认接受注册、密钥或商业采购。
不迁移 Vue 到 React，不为 Nuxt UI 引入 Nuxt 应用框架或 SSR，也不顺带替换 ECharts 和业务状态层。

## 2. 项目基线与迁移规模

实际锁定版本来自 `frontend/package-lock.json`，不能把 package.json 中的最低版本当作安装版本：

| 依赖 | 当前锁定版本 |
|---|---|
| Vue | 3.5.27 |
| Element Plus | 2.13.2 |
| Vite | 5.4.21 |
| ECharts | 5.6.0 |

源码静态计数（排除生成声明、生成 API 类型和单测；模板排除 HTML 注释；不是运行时 DOM 数量，也不是准确工期）：

- 63 个 `.vue` 文件中，60 个包含 `el-*` 起始标签。
- 56 种不同组件标签，共 1469 处起始标签。
- 37 处表格、249 处表格列声明、20 处对话框、20 处表单、11 处日期选择器。
- 25 个样式文件含 `.el-*` 引用，涉及 59 种类名、218 次引用。
- 19 个 E2E spec 中，15 个在 155 行代码里直接引用 `.el-*` 类。
- 还有通知、确认框、表单实例与类型等脚本依赖，不能只做标签替换。
- 42 个源码文件直接导入 Element Plus；例如确认取消转为 `false`、表单校验 Promise、全局报错去重等现有约定都必须保留。

当前已做的优化：

- `vite.config.ts` 通过 resolver 按需导入组件 JS，页面路由已拆分。
- `main.ts` 整体前置导入组件 CSS 是既有 #285 修复，用于避免异步组件样式覆盖项目主题；不能将其误认为“整库 JS 全量导入”。
- 图表有独立分块；更换组件库不能自动减少图表计算、接口等待或业务派生开销。

目前确认的表格屏外操作、收益卡重复、筛选拥挤等问题，有页面布局和调用方式的原因；新库不会自动修正。
已经投入旧库的工作不是拒绝迁移的理由，但迁移必须计入这些真实行为与回归成本。

## 3. 候选比较

| 维度 | Element Plus 基线 | Naive UI 候选 | Nuxt UI 候选 | shadcn-vue / Reka 手工组合 |
|---|---|---|---|---|
| 交付形态 | 完整组件库，当前已接入 | 完整 Vue 3 组件库 | Reka、TanStack 与 Tailwind 之上的成套 Vue 组件 | 组件源码与底层交互原语，需要项目组合 |
| 暖色与排版定制 | 已有 token，但存在较多内部类覆盖 | 类型化 themeOverrides | Tailwind 与语义主题配置，组件样式可定制 | 控制最直接，也要维护最多自有样式 |
| 数据表 | 现有固定列、展开、排序等已使用 | DataTable 有虚拟化、固定列等能力 | UTable 封装排序、分页、固定列、虚拟化等 | TanStack 提供状态/算法，渲染与部分交互自建 |
| 中文表单和日期 | 项目现有行为已验证 | 有完整表单、日期和中文 locale | 有表单、日历/日期输入及 locale，需要适配现有日期模型 | 需要组合日期、校验、错误反馈与表单状态 |
| 键盘与焦点 | 需要修复调用方式并验收实际页面 | 按实际表格、表单、弹窗验证 | 有 Reka 基础能力，仍需验证业务组合 | Reka 提供原语能力，不替代整页验收 |
| 构建影响 | 最小 | 新库和主题机制，通常不必增加 Tailwind | 增加 Tailwind 4 与 Vite/Vue 插件，核对兼容与类型生成 | 增加组件源码、Tailwind、表格/虚拟化及表单配套 |
| 性能结论 | 已完成代表页基线 | 已完成，200 行表格表现较好 | 已完成，本样本无综合性能优势 | 本轮未测 |
| 长期维护 | 保留现有适配与覆盖 | 维护组件 API 迁移和主题 | 维护库、构建及样式体系配合 | 上游变更与复制进仓库的组件代码均需处理 |

表中能力来自官方文档/源码，并不保证这些能力在同一张复杂表格中能无条件组合。
本项目多行标的名称、账户展开、长徽标、金额副行会产生不同高度；不能用固定 40px 的虚拟滚动演示替代验证。
未知金额、0.085 价格、原币/CNY、日期、只读导入、异步标的搜索等业务语义继续使用本项目 helpers、类型和 API。

### 需要用页面验证的具体边界

- Naive UI 当前 2.45.3：DataTable 有固定列、展开和虚拟化，但横向虚拟化还要求列宽、行高配置，并限制合并单元格。不能只打开一个开关就认定复杂持仓表已适配。
- 所读 Naive 默认表头排序/筛选实现以 click 触发，排序图标是 span；未看到足以证明完整表头键盘/读屏契约的处理。需要验证可聚焦、Enter/Space 排序、排序状态播报；必要时评估少量补齐是否值得，不能直接宣称交互更优。
- Naive 2.45.0 使用 `vue-jsx-vapor` 编译链，但官方日志说明产物仍为 VDOM；不将名称当作性能飞跃证据。后续焦点、弹窗修复也应纳入候选版本锁定。
- Nuxt UI 4.11.3 的 UTable 基于 TanStack Table 8.21.3；其虚拟化源码使用估算行高与 `virtualRow.size`，未见自动 `measureElement` 测高接入。长名称、徽标、展开内容需实测。
- Nuxt 官方明确虚拟化不支持行固定；列固定是另一能力，需明确列宽。行选择的 Tab/Enter/Space 支持也不等于全单元格方向键导航。
- PrimeVue 当前 DataTable 虚拟列表仍需要固定 `itemSize`；不能从分别支持展开和虚拟化推定两者适合任意行高组合。

这些是对所查版本文档/源码的限定性结论，不是对候选完整无障碍或性能的自动化测试结果。

### PrimeVue 的版本与授权边界

官方公告明确：原有 MIT 版本继续保持 MIT，PrimeVue 5 起采用 PrimeUI 授权、不再以开源方式发布。
符合条件的 Community 可免费使用，但需要资格确认与每年密钥续期；不能把“免费”直接等同于 MIT 开源。
因此不将“最新 PrimeVue 仍是全量 MIT”作为选型依据，也不为了保留旧授权而未经评估新迁入旧主版本。
如用户希望把非开源授权方案也加入，另行核对具体版本与使用条件；本轮不注册、不购买。
来源：[PrimeUI 官方变更公告](https://primeui.dev/nextchapter)。

### Nuxt UI 与手工 shadcn 组合的边界

Nuxt UI 官方提供普通 Vue + Vite 接入，不要求迁移 Nuxt；当前公开仓库为 MIT。
它已经封装一部分表格、表单与浮层组合，相比直接复制 shadcn 组件更少需要自建。
但 Tailwind、Vite 插件、locale、日期对象及主题配置仍有接入成本；当前 CI 先 typecheck 再 build 的顺序必须继续可用。
锁定候选版本后按其实际依赖阅读 TanStack 文档，不把不同主版本的示例混用。
已核对 Nuxt UI 4.11.3 支持 Vue/Vite；其 Tailwind Vite 插件 4.3.3 的 peer 范围包含现有 Vite 5.4.21，Reka 2.10.5 也接受现有 Vue 3.5.27，不因其仓库开发依赖较新就强制全项目升级。Node 要求 `^20.19.0 || >=22.12.0`，仍需核对实际构建环境。
Nuxt UI 提供简体/繁体语言包；日期 `DateValue` 与本项目 `YYYY-MM-DD` 在边界转换，不能顺手转成 UTC 时间。表单可用自身 validate，不强制增加新的 schema 校验库。
浏览器兼容与字体/图标加载方式按现有部署需求验证；使用本地系统字体，不因换库引入页面必需的外部字体服务。

## 4. 最小对照：一页内容，两种替代实现

**用户已于 2026-10-02 确认「同意，先做对照」；此授权仅覆盖隔离原型与测量，不含全站迁移。**

1. 在隔离分支/目录，用当前 Vue + Vite 构建方式保留现有 Element Plus 版本作为基线。
2. 只做一份代表性验证页面：持仓表格片段、账户/日期筛选、打开交易表单弹窗；分别用 Naive UI、Nuxt UI 实现相同交互。
3. 使用同一份合成金融数据、同一格式化规则、同一暖色目标与相同可见字段，不给新方案减少内容来制造速度优势。
4. 表格覆盖标的多行、原币/CNY、未知金额、价格精度、排序、账户展开、固定操作列；表单覆盖中文日期、金额输入、校验与关闭后重开。
5. 保持现有分页策略；按现有默认 50 行、可选 200 行做主要样本，较大列表只作为补充压力检查。虚拟化只在可完整保留交互且确有收益时试用。
6. 两个候选按需导入；不把全部 UI 库一起打入同一个页面，避免相互样式污染与体积统计失真。
7. 输出同视口截图、短操作对照、构建与浏览器测量、迁移所需胶水代码；用户据此决定 D4。

不在验证页复制整个后端、创建通用组件框架、移植全站、比较所有市场组件库或设计未来扩展点。
若一个候选在构建兼容、必要交互或许可边界上已经不满足需求，记录原因后停止，不为补齐演示投入额外框架开发。

## 5. 多维验收：如何判断“值得换”

| 维度 | 检查方式 | 不能当作通过证据的情况 |
|---|---|---|
| 加载性能 | 生产构建，分别记录初始与路由新增 JS/CSS、gzip；同设备同缓存条件测渲染 | 比较 npm 包大小、下载量，或把全站所有分块算成首屏 |
| 操作性能 | 同数据量测筛选、排序、打开弹窗、展开行和滚动的响应及长任务 | 用只有纯文本的新表对比包含徽标和交互的旧表 |
| 交互 | 键盘可达、焦点返回、中文输入/日期、错误定位、操作防重复、窄屏触控 | 只看桌面有数据截图，或引用“支持无障碍”宣传 |
| 视觉与阅读 | 同暖色方案、真实长度文字、密表与长文检查；用户审阅 | 默认皮肤更漂亮就认定架构更优 |
| 业务完整性 | 同一 fixture 的金额/日期/空值/账户/分页语义完全一致 | 自动取整、未知变零、仅对当前页筛选等退化 |
| 维护与迁移 | 统计项目额外封装、CSS 覆盖、依赖与测试修改，检查构建/类型/版本要求 | 只数模板代码行数，忽略新增依赖和自建交互 |

浏览器重复测量区分正常波动，不承诺尚未测得的提升比例；保留版本、数据量和测试条件。
选择标准：必要财务与操作行为不能退化；性能、交互、样式控制或维护中有可说明的实际收益，整体收益足以覆盖迁移成本。
如果交互改善明显但包略大，或性能更好却增加大量维护，应把取舍交给用户，而不是用一个随意加权总分替用户决定。
若只是性能瓶颈，先定位具体根因；可能只需分页、减少重复渲染或替换单个表格，无需全站迁库。

## 6. 如果确认全站替换

1. 用户确认 D4 后，把选中库写入整体计划；D2 导航形式仍按独立确认结果执行。
2. 先建立最小主题、全局提示/确认、必要基础控件与页面外壳。共享封装只覆盖真实重复用途，不写兼容所有旧 API 的适配层。
3. 按整体计划的持仓交易、统计股息、研究阅读及余页分组替换；复用原取数、会计函数、状态和生成 API 类型。
4. 过渡期新旧组件按页面隔离，避免一张表单混两套错误/焦点行为；不把双库共存当作永久架构。
5. 每个独立 PR 附行为与截图验收，E2E 逐步改为角色、标签和稳定标识，保留必要的具体组件测试。
6. 最后移除 Element Plus 的组件依赖、resolver、CSS、类型与死样式；最终构建重新验证体积和交互，不能用迁移中双库体积作最终结论。
7. 本轮不会因换库增加数据库迁移或更改投资收益算法；部署按原项目流程另行执行。

如果证据只支持局部替换，明确具体页面/组件与收益后由用户确认，避免同时维护多套重叠基础组件。
